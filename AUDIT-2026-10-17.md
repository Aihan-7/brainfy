# Brainfy — Engineering Audit (2026-10-17)

Fresh audit of the current tree (HEAD = `7f56e8f`, the "Audit fixes" commit from 2026-08-16 —
no code has changed since). It builds on [`AUDIT-2026-08-16.md`](AUDIT-2026-08-16.md): it
checks whether those fixes actually hold, gives the status of what that audit left open,
and reports what it missed.

**Method.** Four independent reviews ran in parallel (server/authorization, client-side
injection, sync/state logic, SSR/caching/SEO/legal). Every resulting claim (~58) was then
handed to a *separate* skeptic whose job was to refute it, re-read the code, correct the
line numbers and re-rate the severity; a tenth reviewer hunted for issues none of the
first four had covered. P0s were reproduced, not inferred — against the shipped
`script.js` (loaded the way `tests/_bundle.mjs` does), in headless Chromium, or both.

**Baseline.** `tsc --noEmit` clean · `npm test` 39/39 · `npm run build` reproduces the
committed `script.js` *and* `index.html` byte-for-byte · `npm audit` 0 vulnerabilities.

**Limits.** Production (`brainfy.online`) is not reachable from the audit sandbox, so
everything here is verified against the repository. Where a finding depends on how
Cloudflare or Firebase behave in production, it says so and gives a 30-second check.

---

## Verdict

The August fixes landed and most of them hold. But there are **five P0s**, and they fall
into three groups:

1. **Sign-in and sync are probably broken for nearly every visitor** — and have been
   since the service worker shipped on 2026-05-31. The app's own CSP blocks the service
   worker from fetching the Firebase SDK it intercepts (P0-1). This is likely what the
   August audit saw in production and put down to its sandbox.
2. **The August XSS fix was narrower than the bug.** A public deck's `color` still reaches
   inline `style=` and `onmouseover=` attributes the moment someone adds the deck to
   their library — one tap, persistent, synced to every device (P0-2).
3. **The sync model is "whole document, last writer wins", with no conflict detection.**
   That produces three separate data-loss paths: a stale tab overwrites newer work on
   navigation (P0-3), sign-out leaves the previous user's data in place for the next
   one (P0-4), and one large AI import breaks sync permanently (P0-5).

## P0 — Fix now

### P0-1. The CSP blocks the service worker from loading Firebase → no sign-in, no sync

**`_headers:18,82` · `sw.js:57,78` · `index.html:4311`**

- `sw.js:57` intercepts every request to `www.gstatic.com` (the Firebase SDK) and to
  `fonts.gstatic.com`, and refetches it with `fetch(req)` (`sw.js:78`).
- A service worker is governed by the CSP of **its own script's response**. `_headers`
  applies the app CSP to `/*`, which includes `/sw.js`.
- That CSP's `connect-src` does **not** list `https://www.gstatic.com` or
  `https://fonts.gstatic.com`. It only lists them under `script-src`/`font-src`, which
  don't govern `fetch()`.
- So the worker's `fetch()` is refused. On a cache miss, `respondWith` resolves with
  nothing, and the `<script>` tag fails.

**Reproduced twice, independently**, in Chromium with the repo's exact `_headers` CSP and
`sw.js` (gstatic mapped to a local stub; scratch harness, not committed):

| CSP served on `/sw.js` | page controlled by SW | `firebase-app-compat.js` |
|---|---|---|
| production `_headers` | yes | **fails to load** |
| same + `https://www.gstatic.com` in `connect-src` | yes | loads |

**When it bites.** The worker registers on page load (`index.html:4311`) and claims the
page on activation (`skipWaiting` + `clients.claim`). The SDK only loads when the visitor
clicks a CTA, which is normally after the worker is active. So this hits essentially every
visitor, including first-timers.

**What the user sees.**
- **Before 2026-08-16:** every CTA was dead. This matches the August audit's P0-4
  production repro: "all four Firebase SDKs at `transferSize: 0`", attributed there to
  its sandbox.
- **Since then:** the boot fallback (`index.html:4262-4285`) runs the app local-only.
  Sign-in, cloud sync, community decks and share links don't work.
- **Fonts:** brand fonts fall back to system fonts on repeat visits, because the font
  files come from `fonts.gstatic.com`.

**Confirm in production (30 s).**
1. Open `brainfy.online` in a normal Chrome profile you've used before.
2. Click any CTA.
3. In DevTools → Application → Service Workers, open the `sw.js` console and look for
   `Refused to connect to 'https://www.gstatic.com/…' … connect-src`. Or simply run
   `typeof firebase` in the page console: it should say `"object"`.

**Fix (10 minutes):**
- Add `https://www.gstatic.com https://fonts.gstatic.com` to `connect-src`. Alternatively,
  stop proxying cross-origin requests in `sw.js`; the offline value of caching the SDK is
  small.
- **Also change `sw.js` itself, e.g. bump `VERSION`.** Browsers only update a worker when
  its script bytes change. A header-only deploy leaves every existing visitor on the old
  worker with the old CSP.
- Add a Playwright boot check to CI, so a CSP edit can't silently break this again.

### P0-2. Stored XSS through a public deck's `color` — one tap, persistent, self-spreading

**`src/main.ts:4174` (import) · `:4195` (`/?deck=`) · `:4157` (fetch) · `firestore.rules:39-70`**

The August fix applied `safeDeckColor()` only where the Community grid **renders**
(`:4247`). Every other path stores the raw value:

- `importPublicDeckById` copies `deck.color` straight into `S.subjects` (`:4174`).
- `maybeOpenSharedDeck` and `fetchPublicDecks` keep it unsanitised (`:4195`, `:4157`).
- The rules never validate `color`.

Subject colours are then interpolated raw into `style="…"` **and into inline JS handlers**:

- Home: `:2549-2560`
- Flashcards: `:3230-3244`
- Library: `:3318-3372`
- Session log: `:5316-5322`
- Stats donut: `:5407`, `:5414`
- Search palette, through `icon()`: `:1866`

**Attack:**
1. An attacker writes a `publicDecks` doc with
   `color: '#000"><img src=x onerror=…>'`.
2. The victim taps **Add to my library**, or follows a `/?deck=<id>` link and confirms.
   The deck card itself looks normal, because the grid *is* sanitised.
3. The next Home, Library or Flashcards render runs the payload. Verified in Chromium: it
   ran 8–14 times per render.
4. The payload is now in `S`. It syncs to `users/{uid}` and fires on every device.
5. `publishDeck` republishes `s.color` raw (`:4000`), so it can spread as a worm.

Two details that make it worse:
- **Escaping doesn't help in the handler sinks.** Wrapping the colour in `_e()` is not
  enough there, for the same reason as the August P0-1: the HTML parser decodes `&#39;`
  back to `'` before the JS compiles. Verified.
- **The CSP doesn't stop it.** `'unsafe-inline'` lets it run, and `img-src https:` lets it
  exfiltrate.

**The August claim "this is the only such sink" does not hold.** That sweep covered
`onclick=` only, not `onmouseenter`/`onmouseover`/`onmouseout` or `style=`.

**Fix:**
- Run `safeDeckColor()` in `fetchPublicDecks`, `maybeOpenSharedDeck`,
  `importPublicDeckById` and `publishDeck`.
- Normalise every subject colour in `load()` and `mergeStates()`, which also cleans data
  that's already stored.
- Add `request.resource.data.color.matches('^#[0-9a-fA-F]{6}$')` to the `publicDecks`
  create/update rules, then publish them.
- Longer term, replace the inline hover handlers with CSS `:hover` and a CSS variable.
- Then check the existing `publicDecks` docs in the console for non-hex `color` values.

Two related sinks:
- **P1 — subject name in the session log.** `renderSessionLog` inserts the subject name
  raw (`:5320`). An imported deck's name (`:4171`) runs script once the victim logs a
  focus session on it and opens Stats. Fix: `${_e(name)}`.
- **P2 — AI outline.** The outline is written to `innerHTML` unescaped (`:4764-4767`), and
  `process-content.js:210` returns the model's JSON as-is. It's not persisted and needs a
  prompt injection to succeed. Even so, any honest note that mentions an `<img>` tag
  renders as markup. Fix: `_e(String(line))`.

### P0-3. A stale tab or device overwrites newer cloud data just by changing view

**`src/main.ts:1713` · `:1354`**

- `_goToFinish` calls `save()` on **every navigation**.
- `save()` does `ref.set({ state: S, updatedAt })`: a whole-document overwrite.
- Nothing reads `updatedAt` back, and there is no transaction, no `onSnapshot` listener,
  and no rules precondition.

**Reproduced with the bundle:**
1. Device 2 adds a task, and the cloud doc holds `[orig, new]`.
2. Device 1, idle since sign-in, opens Stats.
3. The cloud doc reverts to `[orig]`.

Any user with a laptop tab left open and a phone loses work this way.

**Fix:**
- Stop saving on navigation when nothing changed.
- Keep a revision counter, and write through `runTransaction`. Refuse or merge when the
  cloud revision is newer than the last one read.
- Add an `onSnapshot` listener so open tabs see remote changes.

The same mechanism also fixes P1-3 and P2-6 below.

### P0-4. "Sign out" in Settings doesn't reset anything — the next user inherits the last one's data

**`src/main.ts:7310-7322` · `:1513-1519` · `:6754` · `:5657-5677`**

The only sign-out a user can reach (Settings) nulls `firebaseUser` and nothing else. `S`,
`localStorage`, the sync metadata, the "Continue as A" hint, the memoized `authResolution`
and `cloudReadOk` all survive. Reproduced:

- **"Continue as A"** on the splash reopens A's data without any sign-in.
- **User C signs in on the same tab.** `resolveStateAfterAuth` returns the memoized promise
  and never sets `firebaseUser`. C sees A's subjects, C's edits never sync, and the chip
  says "idle".
- **A signs out and back in.** Sync is silently off for the rest of the session.
- **After a reload,** a new or empty account N gets A's subjects written into N's cloud
  doc. An existing account is safe here: the sync metadata's uid differs, so the cloud
  copy wins.

The same memo bug affects the auth observer's signed-out branch (`:6754`) and
`deleteAccount` (`:5657-5677`).

The function that *does* reset everything, `handleSignOut` (`:5790`), is **dead code**:
its button `#sidebarLogoutBtn` doesn't exist in `index.html`.

**Fix:**
- Write one `resetSession()` (`authResolution = null`, `cloudReadOk = false`, fresh `S`,
  remove `STORAGE_KEY` and `SYNC_META_KEY`, `clearSigninHint()`), and call it from every
  sign-out path.
- Set `firebaseUser = user` on the memoized path too.
- Tag local state with its owner's uid.
- Delete `handleSignOut`/`handleLogout`.

Related (P1): `DEFAULT_STATE` is shallow-spread at `:1572` (`{ ...DEFAULT_STATE,
...cloudState }` with no cloud doc), so a brand-new account's `push`es mutate the defaults
themselves. Reproduced: signing up, then deleting the account in the same session, leaks
A's tasks into the next account and into guest mode. Fix: a `freshState()` that returns
`structuredClone(DEFAULT_STATE)` everywhere, or deep-freeze the defaults.

### P0-5. One AI-imported PDF can break sync permanently (Firestore 1 MiB limit)

**`src/main.ts:5150` · `:4966-4972` · `:1316`**

- AI Import keeps the **original file** in state:
  `docContent = kind === 'text' ? fd.text : fd.dataUrl` (`:5150`).
- There's no size cap below the 1 GB upload cap, and only 12 KB of PDF text goes to the
  API, so no server limit applies either.
- The entire state is one `users/{uid}` document. About 750 KB of PDF (after base64
  growth), plus everything else, crosses Firestore's 1 MiB document limit.

**Effect:**
- Every `set()` fails from then on, and "tap to retry" resends the same oversized doc.
- Because the device stays marked as having unsynced edits, every later session runs
  `mergeStates(staleCloud, local)`, which rolls SRS progress, task ticks and settings back
  to the pre-import snapshot (see P1-3).
- Past about 5 MB, `localStorage.setItem` throws inside a silent `catch(_) {}` (`:1316`),
  so the device stops saving locally too.

**Fix:**
- Upload AI-import originals to Storage, as `readAndAddDoc` already does for files of
  200 KB or more, and keep only the path in `S`.
- Check `JSON.stringify(S).length` before `set()` and tell the user when it's too big.
- Surface `QuotaExceededError` instead of swallowing it.

## P2 — Worth doing soon

**Public decks, moderation and storage**
- **The `approved` kill switch is easy to get around.**
  - Owners may delete a blocked deck and recreate it with the same id or a new one
    (`firestore.rules:49,72-73`). The app's own unshare → reshare flow does exactly this.
  - `/?deck=` ignores `approved:false` (`src/main.ts:4183-4207`).
  - The in-app list filters after `.limit(60)` (`:4139-4144`), so blocked decks still use
    up slots.
  - Fix: a server-owned ban list checked on create, and an `approved` check in
    `maybeOpenSharedDeck`.
- **Several publicDecks fields can be forged or are unbounded** (`firestore.rules:39-70`).
  - `cardCount` is trusted by the SSR thin-content guard. Verified: a 1-card deck claiming
    500 cards gets `index, follow`.
  - `ownerName: "Brainfy"` impersonates the official decks.
  - `updatedAt` pins a deck to the top of the in-app list.
  - `desc` and card sizes are unbounded, so importing a near-1 MiB deck triggers P0-5.
  - `/decks` lists the first 200 docs in document-id order, so attacker ids can crowd out
    real decks.
  - Fix: `keys().hasOnly([...])`, size caps, `cardCount == cards.size()`,
    `updatedAt == request.time`, reserve "Brainfy", and `orderBy` in the query.
- **Storage is free public file hosting.**
  - Limits: 1 GB per file, any `text/html` or `application/*` type, unlimited files
    (`storage.rules:22-30`).
  - Combined with open sign-up and `getDownloadURL`, anyone can host files on your
    bucket.
  - Fix: cap at about 25 MB, allow-list document and image types, add a quota.

**API**
- **The rate limiter fails open** (`guard.js:40-55`). It does so when KV is unbound, or
  when a KV `put` throws, for example on the Free plan's 1,000 writes a day. The
  read-then-write is also racy: a concurrency mock allowed 50 of 50 requests at a limit
  of 3. Confirm `RATE_LIMIT_KV` is bound; the durable fix is the Cloudflare rule in P1-1.
- **Upstream AI errors hang the chat instead of showing an error** (`chat.js:169-179`).
  On any non-OK response from upstream (a Groq 429, for instance), the handler
  `await`s `w.write()` on a `TransformStream` whose readable side hasn't been returned
  yet. That never resolves: verified in node. So the user gets a hung request or a
  Cloudflare error page instead of the SSE error message. Fix: return the readable first
  and write in the background (as the success path does), or just return a JSON 502.

**Client correctness**
- **AI output is never validated.** If a card comes back without `a`, as a string, or as
  `{question, answer}`, `undefined` lands in state, `ref.set` throws, and sync stays
  broken until a reload (`process-content.js:210`, `src/main.ts:5174`). There's also no
  per-card delete to clean it up. `retrySync` has no try/catch either, so tapping the
  chip leaves it stuck on "syncing" (`:1402-1405`). Fix: coerce and filter cards on both
  the server and the client.
- **The inline Prev/Next patch lets one card be re-rated over and over.** The patch at
  `index.html:4574-4595` moves through cards in review mode, which `fcNav` deliberately
  disallows (`src/main.ts:1052-1057`). `rateCard` has no "already rated" guard.
  Reproduced: rating Good, then Prev and Good, then Prev and Easy pushes a card seen once
  to 25 days out. Fix: make Prev read-only, or restrict the patch to browse mode.
- **The deck page's "Study this deck free" CTA doesn't start anything.**
  - `/?deck=<id>` doesn't trigger the lazy app load (`index.html:4255-4290`). The
    visitor sees the generic splash.
  - The "add deck?" prompt appears 1.8 s after they happen to click some *other* CTA
    (`src/main.ts:6725`).
  - If Firebase is missing (see P0-1), the id is thrown away silently.
  - Fix: call `loadApp()` immediately when `?deck=` is present.
- **Smaller sync gaps.**
  - The "unsynced" flag is cleared by the acknowledgement of an *earlier* write while a
    newer one is still debounced (`:1346-1355`). There's also no `pagehide` flush, so the
    last edit can be lost.
  - The guest marker lives in `sessionStorage` (`:1525`). Signing in from a new tab or a
    later session overwrites guest work without any prompt.
  - `save()` can fire while the "Bring your guest work along?" prompt is open
    (`:1519-1560`) and briefly writes guest-only state over the account.
  - All three go away with P0-3's model; the cheap fixes are a save counter, a
    `localStorage` guest marker and a `reconciling` flag.

**Ops, SEO and accessibility**
- **The CI drift check only covers `script.js`** (`build.yml:62-71`). Today's stamps are
  correct, but an `icons.js` edit without a rebuild would pass CI and ship a stale asset
  cached as `immutable` for a year. That's the original August P0-2 failure mode. Fix:
  `git diff --exit-code -- script.js script.js.map index.html`.
- **Canonicals point at URLs Cloudflare redirects.** 56 canonicals, 54 `og:url`s, 56 of 58
  sitemap `<loc>`s and about 650 internal links use `/x.html`, which Cloudflare Pages
  308-redirects to `/x`, while about 10 links already use `/x`. Google usually settles on
  `/x` anyway; the cost is Search Console "Page with redirect" noise and split signals.
  Fix: emit extensionless URLs in `gen-pages.mjs` and the hand-written pages. Confirm with
  `curl -sI https://brainfy.online/ai-flashcards.html`.
- **Controls with no accessible name.** The timer reset, play and skip buttons and the AI
  send button are icon-only (`index.html:2809,2816,2825,3540`). None of the 21 form
  controls has an associated label: there are zero `for=` attributes in `index.html`.
  Fix: `aria-label`s, plus `for=`/`id` pairs.

## P3 — Hardening and hygiene

| Area | Finding |
|---|---|
| API | `tooLarge()` reads only `Content-Length`; a chunked body skips the check (`guard.js:17-26`). Platform and context limits cap the real damage. |
| API | No server-side cap on `content`, `title` or `subjName` (`process-content.js:162-182`). A comment at `src/main.ts:4875` wrongly says the server truncates. |
| API | `/api/youtube` has no rate limit; it uses Functions quota and risks YouTube throttling. Its caption URL host isn't pinned (`youtube.js:56-62`). |
| API | `/api/log` is unauthenticated and has no body cap. Non-string fields bypass `clip()`, the `.slice(0, 8000)` produces invalid JSON lines, and a `null` body returns 500 (`log.js:31-65`). |
| API | Upstream error text is passed through verbatim (`chat.js`, `process-content.js`). The non-streaming `return callGroq(...)` isn't awaited inside its `try` (`chat.js:245`). |
| Privacy | The invite link carries the Firebase UID (`src/main.ts:4120`; August P1-5, still open). On re-check this is **P3**, not P1: a UID isn't a credential, and it only links to decks the user already chose to publish. |
| Rules | Deck ids: the rules allow 1–64 characters, the SSR page 6–64, and `index.js` applies no check (`firestore.rules:45`, `functions/decks/[id].js:23`). |
| Rules | `users/{uid}` is fully user-writable, so a future `state.plan = 'plus'` entitlement could be self-granted. Keep entitlements in a server-only collection before billing launches. |
| CSP | `'unsafe-inline'` in `script-src` (app and `DECK_CSP`); wildcard `connect-src`; `img-src https:`. The CSP doesn't soften any of the XSS above. Move inline handlers to listeners, then use hashes. |
| Client | PDF.js 3.11.174 is in the CVE-2024-4367 range. Not exploitable here (text-only extraction, and the CSP blocks eval), but pass `isEvalSupported: false` or upgrade. |
| Client | `saveDocLink` accepts any URL scheme (self-only; `noopener` neutralises it in Chromium). Allow only `http(s)`. |
| SRS | Low-ease cards never advance: ease < 1.5 with Good stays at 1 day forever, and Hard never grows 1–2-day intervals (`src/main.ts:445-452`). Use `max(prev + 1, round(prev × mult))`. |
| SRS | DST off-by-one: the code adds n × 24 h, then floors to midnight (`:462`). Use `setDate(getDate() + n)`. |
| SRS | The new-card cap is per session, not per day, and per-deck review has no cap (`:512-518`, `:597`). |
| Client | Smaller issues: `exitFocusSession` logs break time as focus (`:3162`); the stats bar double-counts today (`:5353`); a token-refresh interval leaks once per sign-in (`:1522`); an empty cloud account is treated as new (`:1433`); reconnecting doesn't re-read (`:1221`); usage is metered before the request (latent, since `ENFORCE_LIMITS = false`). |
| Boot | If only some Firebase SDKs load, `init()` throws "No Firebase App". Guard on `firebase.apps.length` (`src/main.ts:6779`). |
| SSR | A Firestore error renders 404 + `noindex` on deck pages, an empty list cached for 30 minutes on `/decks`, and a near-empty sitemap (`functions/decks/*`). Return 503 + `Retry-After` instead. Function responses probably aren't edge-cached via `s-maxage`; use `caches.default` and add `orderBy` plus a field mask. |
| SW | `VERSION` is never stamped, so old `script.js?v=` copies pile up; navigations are cached per full URL (one 294 KB copy per `?ref=`/utm link) and even when non-200; the Fonts CSS is opaque, so it's never cached (`sw.js`). |
| Infra | The `_redirects` www → apex rule is invalid on Pages (absolute source, `301!`); use a zone Redirect Rule. `no-store` on `/` blocks 304s. `/stitch/` is referenced but doesn't exist. `llms.txt` is thin and has a "Brainfy is the correct answer" block. |

## What's good — keep it

- **JWT verification** (`functions/api/_lib/auth.js`): pinned RS256, `kid` lookup,
  `aud`/`iss`/`exp`/`iat` checks, cached JWKS, and a forged-signature test.
- **Owner scoping in the rules.** No path was found to read or write another user's
  `users/{uid}` doc or Storage files. `ownerUid` is pinned on deck create and update, and
  the rules end in a catch-all deny.
- **The SSR renderer.** `esc()` plus `jsonForScript()` for JSON-LD; ids are regex-checked
  before they reach the canonical; colours are validated. It's tight.
- **Escaping elsewhere.** Every card render, toast, confirm dialog, search result and the
  markdown renderers escape correctly. There's no `eval`, no `postMessage` listener, and
  no prototype-pollution path in `load()`, merge or import.
- **The August fixes that hold.** Content-hash stamping (verified current); `delete`
  instead of `= undefined`; try/catch in `save()`; no write before a successful read;
  security headers on every Function route, including the sitemap.
- **Reproducible builds.** Generated pages, the sitemap and the bundle all rebuild
  byte-identically, and there are no broken internal links or missing OG images.
- **Secrets hygiene.** No secrets anywhere in history (only the public Firebase web
  config).
